\textbf{NYC TLC Yellow Taxi} \citep{nyc_tlc} provides approximately
3 million trip records for January 2024, stored as Parquet files.
These records contain zone-level location data (PULocationID and DOLocationID,
mapping to 263 taxi zones) but \textbf{no GPS coordinates}. This dataset
is replayed through Kafka for streaming evaluation. Because it lacks GPS,
only SYN and SEM rules apply; CRS rules cannot be evaluated on TLC data.

\textbf{NYC MTA Bus GTFS-realtime} \citep{nyc_mta_bus} provides a live
public feed of VehiclePosition messages for NYC MTA buses, updated at
approximately 30-second intervals per vehicle. This feed requires no API
key and is publicly accessible. Because it includes GPS latitude/longitude
coordinates, all three rule layers (SYN, SEM, and CRS) apply to this
stream.

The Flink streaming engine \citep{apache_flink} processes events in
event time with watermarks and idle stream detection. A watermark strategy
with a 60-second bounded out-of-orderness and a 5-minute idle timeout
ensures that late events are handled gracefully and idle streams do not
block progress.

\textbf{Design principles.} StreamDQ follows three design principles.
First, \textit{rules are authoritative}: ML never overrides a rule-based
violation. Second, \textit{no silent failures}: every rule evaluation
produces either a violation or a confirmation; there is no fallback to
silence. Third, \textit{context-aware thresholds are adaptive}: thresholds
evolve with the data distribution, with a hierarchical fallback mechanism
that ensures graceful degradation when context cells are sparse.

\textbf{What StreamDQ is not.} StreamDQ is not a production-grade system.
It is a research and education platform that demonstrates the feasibility of
streaming GPS trajectory validation. StreamDQ is not batch-oriented;
it processes events in real time as they arrive. It is not an ML-only
anomaly detection system; rule-based validation is the primary detection
mechanism. It does not claim fault tolerance, horizontal scalability, or
operational readiness.

\subsection{SYN Layer: Syntactic Record-Level Validation}

SYN rules operate on individual event records without cross-record state.
They implement hard constraints that reject events with obvious structural
defects.

\textbf{SYN001} checks that all required fields are non-null and non-NaN.
For float fields, it uses \texttt{math.isnan()} to detect NaN values, guarding
against silent NaN pass-through (known blocker B1 in the codebase).

\textbf{SYN002} checks that \texttt{fare\_amount} $\geq 0$. Negative fares
are structurally invalid and cannot represent legitimate transactions.

\textbf{SYN003} checks spatial validity: for GTFS-realtime events, latitude
must be in $[-90, 90]$ and longitude in $[-180, 180]$; for NYC TLC events,
PULocationID and DOLocationID must be in $[1, 263]$.

All SYN rules emit violations immediately upon detection, without waiting for
additional events.

\subsection{SEM Layer: Semantic Plausibility with Context-Aware Thresholds}

SEM rules use context-aware thresholds computed from rolling windows.
Unlike SYN rules (hard constraints), SEM rules allow values outside
context-specific ranges when the range itself is unusual.

\textbf{SEM001} and \textbf{SEM002} use rolling P10/P90 percentiles
computed from a 1-hour sliding window per context key. These thresholds
are looked up from the BroadcastState at evaluation time (O(1) amortized).
For example, a fare of \$45 in midtown Manhattan on a weekday morning may
be within the L0 context bounds but the same fare in a low-fare outer
borough zone at midnight would violate the tighter L0 threshold.

\textbf{GTFSSem002} checks for stale vehicle positions. A GTFS-realtime
position is considered stale if it is more than 5 minutes old relative to
the current processing time. Stale positions indicate pipeline delays or
upstream system failures.

All SEM rules use thresholds from the hierarchical fallback system
(\ref{sec:threshold-hierarchy}). If no threshold is available (all levels
sparsity-exhausted), the event passes SEM evaluation.

\subsection{CRS Layer: Cross-Record Stateful Validation}

CRS rules maintain per-entity state across events. Because PyFlink's JVM-Python
serialization overhead is prohibitively expensive for stateful operations
\citep{apache_flink}, CRS rules are implemented in Java as
\texttt{KeyedProcessFunction} operators invoked via gRPC from the Flink
Python operator.

\textbf{CRS001: GPS Speed Bounds.} We compute the Haversine great-circle
distance between the current and previous position:

\begin{equation}
d = 2R \cdot \arcsin\!\left(
\sqrt{\sin^{2}\!\frac{\phi_{2}-\phi_{1}}{2}
+ \cos\phi_{1}\cos\phi_{2}\sin^{2}\!\frac{\lambda_{2}-\lambda_{1}}{2}}
\right)
\end{equation}

where $R = 6{,}371$ km (Earth mean radius), $\phi$ is latitude,
and $\lambda$ is longitude in radians. Speed is
$s = d / \Delta t \times 3{,}600{,}000$ km/h.

A violation is emitted if $s < 2.0$ km/h \textbf{or} $s > 100.0$ km/h.
An additional guard condition detects sustained low speed ($s < 0.5$ km/h
for $\Delta t > 60$ s), which may indicate a stuck GPS or off-route vehicle.
The primary threshold is $[2.0,\ 100.0]$ km/h; the secondary condition
is a GPS-jitter guard only.

CRS001 is evaluated on every GTFS-realtime VehiclePosition event for which
a prior position exists in the per-vehicle state. The first position for
each vehicle initializes the state without producing a violation.

\textbf{CRS002: GPS Jump Detection.} For every pair of positions of the
same vehicle within a 30-second window, we compute the Haversine distance.
If the distance exceeds 400 meters, a GPS jump violation is emitted.
This rule detects instantaneous position teleportation that is physically
impossible for an urban bus traveling at 30-second update intervals.
At a mean speed of 45 km/h, a bus travels approximately 375 meters in
30 seconds, just below the 400-meter threshold.

\textbf{CRS003: Event Deduplication.} We compute a content hash
SHA256(trip\_id $+$ timestamp $+$ GPS coordinates) for each event.
If the hash is already present in the per-trip deduplication state (a
RoaringBitmap with 300-second TTL), a duplicate violation is emitted.
CRS003 is the only CRS rule applicable to NYC TLC (where deduplication
is performed on trip\_id $+$ timestamp $+$ zone IDs).

\textbf{CRS003 limitation (NG-4).} CRS003 recall cannot be measured
because the replay suppression gate in the current code tags synthetic
duplicate events as \texttt{is\_replay=True}, which triggers the gate
and suppresses violation emission. CRS003 precision is measurable;
recall is labeled \texttt{[TIER-3\ UNMEASURABLE]} until NG-4 is fixed.
See \ref{sec:ch3-limitations}.

  }}
  \caption{L0--L5 hierarchical context-aware threshold fallback. For each event
    the system extracts five context dimensions (D1--D5), constructs the L0
    context key, and traverses L0--L4 until sufficient samples are found.
    Each level provides P10/P90 bounds from rolling windows. L5 physics priors
    are the hard fallback. L0 covers only 2--5\% of events due to zone-hour
    sparsity. D4 (External) is a stub.}
  \label{fig:l05-hierarchy}
\end{figure}

The context key function $ck(e, L)$ maps an event to a string key at fallback
level $L$:

\begin{equation}
\begin{aligned}
ck(e, L0) &= f"H{e.hour:02d}_{\text{zone\_cat}(e)}_{\text{WE|WD}(e)}" \\
ck(e, L1) &= f"{bucket(e.hour)}_{\text{zone\_cat}(e)}_{\text{WE|WD}(e)}" \\
ck(e, L2) &= f"{bucket(e.hour)}_{\text{borough}(e)}_{\text{WE|WD}(e)}" \\
ck(e, L3) &= bucket(e.hour) \\
ck(e, L4) &= \text{"global"} \\
ck(e, L5) &= \text{"physics"}
\end{aligned}
\end{equation}

The threshold retrieval function evaluates levels L0 through L4 in order,
returning the first level with sufficient samples:

\begin{equation}
\text{get\_threshold}(e, f) \Rightarrow
\begin{cases}
\text{BroadcastState}[L0][ck(e,L0)][f] & \text{if } count \geq 100 \\
\text{BroadcastState}[L1][ck(e,L1)][f] & \text{if } count \geq 50 \\
\text{BroadcastState}[L2][ck(e,L2)][f] & \text{if } count \geq 25 \\
\text{BroadcastState}[L3][ck(e,L3)][f] & \text{if } count \geq 10 \\
\text{BroadcastState}[L4][ck(e,L4)][f] & \text{if } count \geq 5 \\
\text{physics\_prior}(f)                 & \text{always}
\end{cases}
\end{equation}

The minimum sample thresholds are derived from power analysis: at L0,
Cohen's $d = 0.30$, $\alpha = 0.01$, power $= 0.80$ requires $n \geq 100$
samples per cell for the context-specific threshold to outperform the global
threshold by a detectable margin.

BroadcastState provides O(1) amortized lookup for threshold retrieval.
The state is updated hourly by the calibration job; the update is
broadcast to all TaskManagers atomically. State size is estimated at
approximately 25 MB for 10,000 context cells $\times$ 5 fields $\times$
500 bytes per cell.

\textbf{CRS rules use L5 physics priors exclusively.} CRS001 and CRS002
thresholds (GPS speed bounds, jump distance) are physical constraints that
do not vary with context. They are implemented as hardcoded L5 values
with no data dependency. CRS003 (deduplication) similarly has no context
dependency.

\section{Trajectory Quality Scoring}
\label{sec:tqs-design}

We design TQS as a composite score from five \textit{stream-intrinsic}
quality dimensions: dimensions that are computed directly from raw event
properties, without referencing rule violation outcomes.

The five dimensions are:

\begin{itemize}
  \item \textbf{Tm (Timeliness)}: $\text{Tm} = \exp(-\lambda \sigma^{2}_{\Delta t})
        \cdot (1 - \text{stale\_rate})$, where $\Delta t$ is the inter-event
        time delta, $\sigma^{2}_{\Delta t}$ is its population variance,
        $\lambda = 10^{-8}$ ms$^{-2}$, and $\text{stale\_rate}$ is the
        fraction of events older than 300 seconds. Tm $\in [0, 1]$.
  \item \textbf{Cn (Completeness)}: fraction of non-null, non-NaN required
        fields. $C_n = 1 - n_{\text{missing}} / (N \cdot |F|)$.
  \item \textbf{Ac (Accuracy)}: raw field plausibility (fixed bounds, not
        context-adaptive). For NYC TLC: fare $\in [0, 1000]$ USD, distance
        $\in [0, 500]$ miles, passengers $\in [0, 9]$, zones $\in [1, 263]$.
  \item \textbf{Cs (Consistency)}: GPS coherence from raw positions (not
        from CRS001 violations). Uses a 150 km/h bound (wider than
        CRS001's 100 km/h) to detect only physically impossible measurements.
  \item \textbf{Uv (Uniqueness)}: $U_v = 1 - |\{h(e) : e \in \text{window}\}| / N$,
        where $h(e)$ is the content hash. Computed from raw event hashes,
        not from CRS003 violations.
\end{itemize}

The composite TQS V2 formula is:

\begin{equation}
\text{TQS} = \omega_{\text{Tm}} \cdot \text{Tm}
            + \omega_{\text{Cn}} \cdot \text{Cn}
            + \omega_{\text{Ac}} \cdot \text{Ac}
            + \omega_{\text{Cs}} \cdot \text{Cs}
            + \omega_{\text{Uv}} \cdot \text{Uv}
\end{equation}

with weights $\omega_{\text{Tm}} = 0.20$, $\omega_{\text{Cn}} = 0.25$,
$\omega_{\text{Ac}} = 0.20$, $\omega_{\text{Cs}} = 0.25$, $\omega_{\text{Uv}} = 0.10$
(domain-prioritized, V2). These weights are design choices; V1 (equal) and
V3 (consistency-heavy) are pre-registered variants. TQS is non-circular:
all five dimensions are computed from raw event properties without referencing
rule violation counts. This design is distinct from and draws from the
approach described in T-Assess \citep{tassess2025}, adapted for streaming
GPS data and the SYN/SEM/CRS taxonomy.

\section{ML-Augmented Threshold Calibration}
\label{sec:ml-augmentation}

The ML augmentation pipeline runs asynchronously out-of-band, writing
calibrated parameters to BroadcastState every hour. It never blocks
real-time event processing.

Figure \ref{fig:ml-architecture} shows the ML pipeline integration.

\begin{figure}[htbp]
  \centering
  \fbox{\parbox{0.92\linewidth}{
    \centering
    \textbf{[Figure F5: ML Hybrid Architecture — see
    \texttt{figures/F5\_ML\_Architecture.excalidraw.md}]}
    \par\smallskip
    \begin{minipage}{0.90\linewidth}
      \textbf{ML Augmentation Pipeline}\par
      {\small
      Calibration Window $\xrightarrow{\text{1h}}$ BO: GP surrogate $\rightarrow$ BroadcastState\par
      Isolation Forest: anomaly\_score $\rightarrow$ effective\_k $\times (1 + \alpha \times s)$\par
      Rules remain AUTHORITATIVE --- ML never overrides violations
      }
    \end{minipage}
  }}
  \caption{ML-augmented threshold calibration pipeline. Bayesian Optimization
    (Priority 1) runs hourly on a calibration window, tuning k-multiplier,
    IF alpha, and weekend discount. Isolation Forest (Priority 2, conditional)
    scores anomaly confidence per event. Rules remain authoritative at all times.
    LSTM (Priority 4, NO-GO) is excluded.}
  \label{fig:ml-architecture}
\end{figure}

\textbf{Bayesian Optimization (Priority 1, GO).} We use a Gaussian Process
surrogate with Expected Improvement acquisition to maximize F1 on a 1-hour
calibration window with known injection. The 5 hyperparameters tuned are:
k\_multiplier $\in [1.5, 5.0]$, IF\_alpha $\in [0.0, 0.5]$,
weekend\_discount $\in [0.0, 0.5]$, context\_weight $\in [0.0, 1.0]$,
and LSTM\_threshold\_m $\in [50, 250]$ (for LSTM, kept for completeness
though LSTM is NO-GO). The BO loop runs for up to 30 iterations with
10 initial random points; it converges in approximately 15--30 minutes.
If calibration exceeds 15 minutes, the parameters are considered stale
and are not broadcast. BO runs hourly, leaving a sufficient safety margin.

\textbf{Isolation Forest (Priority 2, conditional).} A single global
Isolation Forest \citep{iforest2008} is trained on all NYC TLC events
with 11 features: normalized fare and distance (Z-scores from ThresholdStats),
passenger count, hour (sine/cosine encoding), zone category (one-hot, 4
categories), weekend indicator, and payment type. Isolation Forest scores
each event with anomaly confidence $s \in [0, 1]$. The effective k-multiplier
becomes $\text{effective\_k} = \text{base\_k} \times (1 + \alpha \cdot s)$,
making context thresholds tighter for statistically anomalous events.
This component is activated only if the correlation between Isolation Forest
scores and P90 violations is $\rho < 0.8$. The single global model avoids
the computational cost of maintaining separate models for 6,000+ context cells.

\textbf{XGBoost (Priority 3, conditional).} A scaffold exists for
XGBoost-based threshold prediction, but the training target (optimal
threshold) is undefined. This component will be developed after Phase 3
when BO and Isolation Forest are benchmarked.

\textbf{LSTM (Priority 4, NO-GO).} LSTM trajectory prediction is excluded
for three documented reasons: (1) 6-month historical NYC MTA Bus GPS
archive has not been confirmed to exist; (2) LSTM trajectory deviation
is highly correlated with CRS002 GPS jump detection; (3) LSTM provides
only alert elevation (not authoritative validation) in a research platform.
We re-evaluate only if CRS002 recall falls below 60\% on real GPS anomalies
AND a 6-month GPS archive is confirmed.

\section{Chapter Summary}
\label{sec:ch2-summary}

This chapter described the StreamDQ system architecture. We presented the
overall pipeline (Kafka $\rightarrow$ Flink $\rightarrow$ PostgreSQL/Prometheus)
with two data sources: NYC TLC (zone-level, SYN/SEM only) and NYC MTA Bus
(GPS, all rules). We described the three-layer rule taxonomy (SYN/SEM in
Python, CRS in Java/gRPC), the hierarchical L0--L5 threshold fallback
mechanism, the non-circular TQS design from five stream-intrinsic dimensions,
and the ML calibration pipeline. We emphasized that rules are authoritative,
CRS rules require Java for performance, and L0 coverage is sparse (2--5\%).

Chapter 3 presents the evaluation methodology and benchmark results.
